# D11 homework, 2026-09-29: the typed HIR's relational/scalar split, and whether it is TypedRelationOp

Read-only static homework for decision D11 (what type the scalar leaves of the store resolver's new relational output
should be), at `8eaf187a2` on `compiler/rebuild`. Drafted by a read-only agent and persisted here by the parent session.
Method: grep/sed/awk, one read-only `git log -S`, a regex parse of the 831 native signatures in `builtin/Pure.java`.
Paths relative to `core/src/main/java/com/legend/`. Runtime facts are open questions (§6), not claims.

## Answer

**D11 is not the same as TypedRelationOp.** TypedRelationOp (commit 91024b241, 2026-09-23) groups 16 unary relation
operators so one resolver arm (`StoreResolver.java:535-537`) can rebuild any of them over a resolved source. It has one
reader outside `typed/`. It exists on both sides of store resolution, 5 of its members are also scalar-collection and
class-space operators, and it leaves out 16 relational kinds. D11 asks for a post-resolution vocabulary (scans, a join tree
with ids, `ColumnRef(JoinNodeId, column)`) that does not exist today, and for the type of the scalar expressions inside it.
No existing kind boundary gives that type.

## 2. Relation-valued calls

- 66 native overloads (35 FQNs) return a relation; all but three FQNs have a dedicated record through a CoreFn form
  (`platform/CoreFn.java:33-181`); `relation::lateral` reaches lowering as a `TypedNativeCall`.
- 125 overloads (78 FQNs) return a bare type parameter and can be relation-valued (`at`, `first`, `toOne`, `union`,
  `sort`, …); how many are at run time is not known statically.
- 43 overloads (36 FQNs) consume a relation and return a scalar (`size`, `exists`, `in`, window functions, …).
- `TypedUserCall` must not survive resolution except store-element identities and Subsumed programs
  (`resolver/StoreEscapees.java:46-64`).

## 3. What the store resolver outputs

- 872 typed-node constructions in `resolver/` over 38 of 57 files: TypedLambda 141, TypedVariable 124, TypedPropertyAccess
  116, TypedNativeCall 71 (mostly scalar predicate glue), TypedFilter 60, TypedJoin 35 (in 10 files, not the 26 in 7 the
  W4 audit counted), TypedProject 32, …
- The only run-time post-condition is `StoreEscapees.check` (`StoreResolver.java:211-217`): it throws on JoinSlot, GetAll
  and UserCall; it does NOT check class-form Navigate, MilestonedAccess, NewInstanceCast, GraphFetch or class-typed
  PropertyAccess. The lowerer walls JoinSlot (`Lowerer.java:729-733`) and non-PRE_MAP Navigate (`:1900-1907`); the rest fall
  to the frontier defaults (`:749`, `:3196`).
- **No kind is exclusive to resolver output**: TypedJoin (typer 5 / resolver 35), JoinSlot (3/8), MilestonedAccess (4/14),
  Navigate (10/7), TableReference (typer 3), FrameRef (typer 2), AsOfJoin (typer 4). A pure relation query passes through
  unchanged (`resolver/Space.java:18-19`), so relation-space kinds routinely exist before resolution.

## 4. What the lowerer reads

- Root dispatch (`Lowerer.java:300-366`) chooses relation vs scalar by `Type.schemaView(spec.info().type()) instanceof
  RelationType` (`:320`); `relation()` (`:511-755`), the scalar chain (`:2422-3226`), `windowScalar` (`:2277`).
- Kinds lowered on both paths: Filter, Slice, Drop, Limit, SortBy, Cast, From, NativeCall, PropertyAccess, Map,
  SerializeGraph, Concatenate; and every R kind in scalar position through the catch-all (`:3135`).
- 73 lines in `lowering/` inspect relation-ness at run time; about 38 of them choose a path or arm by type (Lowerer 16,
  CollectionRelations 4, RelationPredicates 4, ValueCollectionOps 3, Scalars 5, Render 3, Fold/StoreLane/StampCensus 3).
  In `resolver/` the same inspections are 151 lines; class inspections 472; a per-node `Space` memo decides object vs
  relation space at run time (`Anchors.java:140-150, 201-255`).
- The lowerer itself mints 18 typed nodes (e.g. TypedSlice/TypedLimit from `at`/`first`, `:513-536`).

## 5. TypedRelationOp

Introduced by 91024b241 ("Relation operators are one kind, and the resolver covers them all: pivot plans"), after
TypedPivot was missing from the resolver's per-operator arms. One reader outside `typed/` (`StoreResolver.java:535-537`);
zero in `lowering/` and `compiler/spec/`. It does not tell which side of resolution a node is on.

## 6. What each D11 option would cost (static)

| option | records | surface affected | what javac proves | run-time type decisions removed |
|---|---|---|---|---|
| A: whole TypedSpec as leaves | skeleton records only; ColumnRef as a 78th kind | resolver tail, lowering entry | nothing about leaves (27 R + 22 A kinds legal in a leaf) | none |
| B: sealed Scalar subset + ColumnRef | 25 kinds implement Scalar unchanged; each of the 22 A kinds is either marked (no proof) or split into scalar and relational twins (+22 records); a subquery kind for scalars over relations | per split kind, e.g. NativeCall named in 112 files, Variable 71, PropertyAccess 60, Collection 58, Lambda 81, Map 39 | top-level kind only unless child fields narrow to Scalar, which breaks pre-resolution uses such as `exists(Person.all()…)` | with splits: the relop guards (`Lowerer.java:2828-2939`) and the root choice (`:320`); marker only: none |
| C: a new scalar family (Calcite RelNode/RexNode) | ~40+ records and a TypedSpec→scalar converter | the lowerer's scalar chain (~800 lines), Scalars (3,476 lines), 49 lowering files; the executor reads resolver output too | leaves and their children, by construction | all of lowering's, but they move to the converter unless the resolver emits the new family directly |
| D: annotations | none | opt-in readers | nothing (fails rule 0.10) | none |

Common to B and C: the lowerer's 18 internal desugars and the resolver's 71 native-call mints retarget; ColumnRef replaces
today's by-name column reads (116 PropertyAccess + 124 Variable constructions in the resolver).

## Open questions that need a runtime census

1. Which kinds actually occur as scalar leaves of resolver output, and how often a leaf holds a relational child. Probe: a
   census walk at `StoreResolver.resolve`'s exit recording `(kind, relationValued, classValued)` per node in scalar
   position, over every suite.
2. Whether each of the 22 ambiguous kinds is ever relational after resolution. Probe: the same census plus counters at the
   `relation()` default and the scalar catch-all, keyed by kind.
3. Which of the 125 polymorphic native overloads appear relation-typed. Probe: a callee counter at the six relation-position
   native arms and the default.
4. Whether the unchecked class-space kinds ever survive resolution. Probe: flag them in census 1 (also the seed of the
   W1.3 verifier for H).
5. How the five ambiguous relops split by space (class / relation / value list) before and after resolution. Probe: a
   counter at `Anchors.spaceOf` and a lowering-side `relationValued(source)` counter.
