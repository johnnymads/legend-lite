   satisfied only if the bridge lands in W1.2's first push.

4. W1.10c depends on a new engine-runner entry point; "runs the same model, query and … data" describes a capability

7. W1.8 depends on a MIR that W5 creates.

## Top risks

1. **Sizes.** Only W1.1b, W1.5, W1.9, W1.10(a–c) carry sizes. Per-item judgement for W1 totals **~29–49 sessions** vs the
   stated ≈14–22; the biggest under-sized: W1.2 (four items in one), W1.3 (7 unlisted pipeline files + nested passes),
   W1.10 (a new mutator, a new engine entry point, a new predicate generator). "W0 ≈2–4 sessions left" must also hold all of
   W0.6's pushes plus W0.4 and W0.7 (NV).
2. **Tooling assumed but absent:** `tools/metrics`, a heap probe, a compile-only query set, an HIR/SQL printer, a fixture
   mutator, an engine rows runner, an EP check API, a jdeps reader, a pure negative-corpus harvest — none named as a
   prerequisite.
3. **Counts that do not reproduce:** `instanceof Typed*` 1,313 vs 1,781; store→lowering/plan 15 vs 13; parser error sites
   24 vs ~600 raise points; the "394 sites" rebuttal counts the wrong thing (the two call records have 100). Gates built on
   shrink-only baselines need re-measured, defined counts.
4. **Owner disagreement:** H4 §3.6 puts the LSP in W6.4; the plan in W1.2.
5. **W0.4 product-behaviour change:** removing `CanonicalRenderSql`'s always-on stabilize changes assert-surface ordering
   outside the harness — needs an explicit "no product user" record or a register row.
6. **Machine/memory cost:** W1.1d's ten reference-lane runs (8 GB each; one with a cold 12 GB `ref_dump`) and W1.0b's
   100K + reference-lane numbers need a quiet machine; CI memory (16 GB on `ubuntu-latest` only for public repos) NV.
