## Cross-cutting observations

- **Four client type tables in this group, with three unknown-type policies.** The tables are result.ts:93 `pureTypeOfArrow` (Arrow name to Pure, unknown becomes `'Unknown'`), infer.ts:54 `sqlTypeOf` (DuckDB name to lite DDL, unknown becomes VARCHAR(4096)), infer.ts:114 + lite-facts.ts:111 (DDL name to Pure, unknown becomes `'String'`) and relation-type.ts:33 `pureType` (engine/lite name to Pure, unknown throws). Their vocabularies do not line up: lite-facts emits `Byte/Other/Distinct`, which `pureType` throws on; `pureType` passes `Date` where Arrow says `StrictDate`. Replacement: the compiler's RelationType / plan columns in ONE closed Pure vocabulary. The client keeps only an enum check.
- **Raw SQL is still typed from Arrow in the client** (duckdb.ts:244/300 via result.ts:93, on both the local and the warehouse plane). Readers: upload DESCRIBE/count, snap preflight count. Replacement: nothing needs a type for these (counts are one number, and DESCRIBE should move server side), so `pureTypeOfArrow` can be deleted once model inference moves.
- **Plan types replace names, not values** (runner.ts:198). Cells are still decoded by client code chosen from the ARROW type (duckdb.ts:154-207), so a column's declared type and its JS representation can disagree: Decimal as float/string, Integer as number/string, StrictDate vs DateTime both `Date`. Replacement: database-rendered, type-directed cells (e.g. the server renders DECIMAL/BIGINT as exact strings and DATE as ISO `YYYY-MM-DD`), decoded per plan type.
- **Date handling bugs at the decode boundary**: DATE becomes a local-midnight `Date` (years 0-99 go to 19xx, and any UTC read shifts the day east of UTC), naive TIMESTAMP becomes a UTC instant shown in the local zone, microseconds are cut to milliseconds, and TIME/INTERVAL arrive as bare numbers. Replacement: the server delivers date and timestamp values as typed text in the column's Pure type. Only presentation formatting stays client-side.
- **Cross-plane value divergence**: the engine plane (engine-remote.ts:90) keeps dates as strings and already-rounded JSON numbers, while the DuckDB/warehouse planes give `Date` objects and number-or-string decimals. The same cube therefore behaves differently per plane. Replacement: one server-rendered cell encoding for every plane.
- **JSON.parse precision loss** (pure-v1.ts:124) rounds BIGINT and DECIMAL cells before any typed code runs. Replacement: the server sends exact numerics as strings, or the client uses a decimal-safe parse keyed on plan column type.
- **Mixed-representation columns**: `toScalar`/`decimalToScalar` return a number for small values and a string for large ones in the SAME column. Every downstream comparator, sort, sum or `typeof` test (outside G5) inherits this. Replacement: one representation per Pure type, fixed by the plan.
- **The client writes the model's DDL** (infer.ts:196-275 via `sqlTypeOf`), with real mapping bugs: unsigned ints become VARCHAR, HUGEINT/UBIGINT become BIGINT, TIMESTAMPTZ loses its zone, TIME/UUID/BLOB/TIMESTAMP_NS become VARCHAR(4096), and bare DECIMAL becomes (38,6). On the warehouse plane the server already owns the catalog (warehouse.ts:41). Replacement: server model/DDL generated from the database's own catalog (DuckDB DESCRIBE server-side for uploads).
- **Type guessing happens in the tab**: DuckDB's CSV/JSON sniffers (upload.ts:94-104, remote.ts:87). These are not hand code, but they are type inference on the client side of the line. Replacement: server-side ingest + DESCRIBE, or the same sniffer run by the server.
- **Measure/dimension default by type** (infer.ts:171, fractional means measure). It is a type-driven DECIDE fed by the client-derived type rather than the compiler's. Replacement: compiler relationType type + a server-side default rule (and it duplicates snapshot.ts `isFractionalType`).
- **Two plan-type shapes and two type-stamping sites**: HTTP plans are read via `tdsColumns` (planner.ts:67) and WASM plans via RelationType (wasm-planner.ts:345). Remote rows are typed by the execute builder (engine-remote.ts:97), not by `typedByPlan`. Replacement: one shape (RelationType of the query) stamped in one place.
- **`'Unknown'` escape type** is still produced in two places (result.ts:135, engine-remote.ts:97 with no builder), and `typedByPlan` passes rows untyped when a plan has no columns. These contradict "a name it does not know is an ERROR" (relation-type.ts:11). Replacement: require compiler columns and refuse otherwise.
- **Precision/scale and multiplicity are dropped** by `relationColumns`/`tdsColumns` (only `rawType.fullPath`/`type` are read), so Decimal(p,s) scale for display, and Varchar length, are unknown to the client. Replacement: pass `typeArguments`/`relationalType` from the compiler.
- **Dead generated tables**: `SQL_NAME_TO_RECORD` and `RECORD_TO_PURE_KIND` (lite-facts.ts:23, 79) have no importer. `GRAMMAR_TYPE_KEYWORDS` is test-only. `PURE_KIND_BY_SQL_NAME` has one consumer (infer.ts:118). All can be deleted once model inference moves server side.
- **Snap tables are typed twice**: by the Arrow import (duckdb.ts:370-399 / snap.ts:225-236) and separately by the model text written from catalog names (infer.ts), with no reconciliation. Replacement: the server writes both the snap source SQL and the model from one catalog read.
