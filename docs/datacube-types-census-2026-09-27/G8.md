## Cross-cutting observations

- **Kind is a type decision in disguise.** Seven UI sites (panel-kit.ts:93-107 hub; editor.ts:317,345; panel-dimensions.ts:161; pivot-panel.ts canGroup; columns-panel.ts groupable; menu.ts canGroup/isMeasure; editor.ts:173 applyToSnapshot) all consume `kindOf` = `isNumericType(type)` (snapshot.ts:108-111,151). Once the compiler supplies the type (relationType), the default kind should be one server-computed fact per column, not re-derived per consumer.
- **Two filter-operator tables.** menu.ts:287 `filterOperatorsFor` vs ui/filter-editor.ts:107/175 `dataTypeOf`/`operatorsFor`. They disagree: the menu knows no `Timestamp`, `StrictTime` or Variant, so those cells get no menu filter. One table keyed by the compiler's type (or a server "operators for type" fact) replaces both.
- **Numeric type set spelled at least three times** in reach of this group: snapshot.ts:171 (`Integer`+Float/Number/Decimal), menu.ts:304-307 (same four), filter-editor.ts:113 (`isNumericType || Number`). No precise-primitive names (TinyInt, BigInt, Double, Varchar, Timestamp) appear in menu.ts — if the planner ever reports precise types, every name switch here silently falls to `default`.

'Derived'`, panel-column.ts:256 `'Derived'`. Under the compiler-types ruling, a calculated column's type is `lambdaRelationType` of the query that contains the extend; the `'Derived'` pseudo-type and the `'String'` default should be deleted.
- **Filter values carry their type only as a JS representation.** menu.ts:108/830 store the raw cell value; menu.ts:361-368 and serialize.ts:116-124 re-derive "what kind of literal" by `typeof`/`instanceof`. Replacement: the server literal writer takes (value, column's compiler type) and returns the Pure literal, so a DECIMAL/BIGINT/DateTime cell is written exactly.
- **Temporal literal is local-clock and seconds-precision** (serialize.ts:106-114, used by menu.ts:364): a DateTime filter from a click is in the browser's zone and drops milliseconds, and midnight DateTimes collapse to date literals. Moves to the server literal writer plus database-rendered values.
- **Pivot result columns show the wrong type** (columns-panel.ts:520): the parent measure's source type instead of the aggregate result type; the typed plan's `tdsColumns` (compiler: plan columns) has the real one per pivot column.
- **Dead type plumbing**: `SelectorColumn.type` (columns-selector.ts:29) is filled by panel-kit.ts:79-81,103 and never read — delete it and the three defaults feeding it.
- **Doc vs code contradiction on the kind default**: docs.ts:43-53 and `kindOf` treat every numeric (Integer included) as a measure, while snapshot.ts:178-184's comment says integers default to dimensions. Decide the rule once when it moves server side.
- **Samples promise types the sniffer likely does not produce** (samples.ts:167-168: "integer … decimal"; DuckDB's default CSV candidates have no INTEGER or DECIMAL — verify), and the `n_big` column is corrupted by JS double arithmetic above 2^53 (samples.ts:172). If types are to come from the server/DB catalog, the stress fixtures should be judged by the compiler-reported types, and `n_big` should be generated as text (e.g. BigInt) to exercise real > 2^53 values.
- **Zone-less timestamps in every fixture** (samples.ts:138-139, 176-178, 199) are the right probe for the local-midnight/UTC decode bugs elsewhere; keep them as the regression inputs when conversion moves to database-rendered values.
