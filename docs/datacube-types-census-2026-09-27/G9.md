## Cross-cutting observations

1. **The TRADES column types are written by hand in 4 client places**: boot.ts:316-327, engine-cases.mjs:16-25, engine-cases.mjs:208-217 and main-engine.ts:47-56. Both legend-lite and legend-engine serve it, so even main-engine.ts's "declared rather than discovered" is unnecessary.
2. **The numeric test is re-implemented, narrower, twice**: `type === 'Integer' || 'Float'` at boot.ts:565 and stress.ts:173. The src rule, src/snapshot.ts:171 `isNumericType`, also admits `Decimal` and `Number`, so DECIMAL columns (which src/infer.ts types as 'Decimal') miss key-like formatting and every numeric stress operation. **Replace with** compiler types plus one owner of "numeric" (server-side, or a single client helper over compiler types).
3. **Client model inference is the entry point for all uploaded and warehouse types**: boot.ts:639 and 677, stress.ts:158, and `setModel` in main.ts:58. DuckDB/warehouse SQL type names go through the client table in src/infer.ts to Pure types and model text. **Replace with** server model/DDL (the server reads the DB catalog and writes the model) plus lambdaRelationType. The warehouse path is the clearest case, because the server already holds the catalog.
4. **Column role (dimension/measure) is inferred from type and from a "key-like" heuristic**, then drives formats (boot.ts:558-569), harness choices (stress.ts:171, verify-smoke.mjs:159-162) and assertions (verify-upload.mjs:140-148, 326-340).
