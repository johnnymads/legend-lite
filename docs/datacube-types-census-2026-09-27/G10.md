# G10 type census: `datacube/demo/verify-features.mjs`

Scope: the browser verification harness, read in full on disk (lines 1-4815, plus the trailing newline). It drives the real page with Playwright against a generated sample CSV. Every type fact it meets therefore comes from this chain: DuckDB CSV sniffing, then `DESCRIBE`, then `src/infer.ts` (`sqlTypeOf`, `PURE_KIND_BY_SQL_NAME`, `kindOf` = fractional -> measure), then the generated `###Relational` model, then `typeColumns` / `lambdaRelationType` (plan.ts), then snapshot columns, then the UI.

Sample schema (src/samples.ts `sampleCsv`), for reference: trade_id int, trade_date date, booked_at timestamp, region/desk/book/quarter text, year int, notional/pnl 2-decimal text, quantity int, settled true/false.

All rows are HARNESS sites. The second category code names the product behaviour the harness exercises or depends on.

## Cross-cutting observations

- The harness never asks the server for a type. Every type-dependent check chooses its columns by hard-coded sample NAME (or position, `GROUP_COL = 3`) and reads type consequences off the DOM: kind classes, the Decimals field, the operators offered. Once types move server side, each check should first read the relationType (from `lambdaRelationType`, or the plan's `tdsColumns`) and select columns by type.
- Heatmap selection (1533) infers "numeric" from a column-name regex. That is the exact guessing the ruling forbids, and it lives in the harness.
- The check at 2571-2608 is titled and commented as "learns its TYPE from the result", and it proves the type only indirectly through a 2-decimal display default. It contradicts the "types come from the compiler (no result-learned types)" ruling in wording, and should assert the compiler's answer for `uplift` directly.
- 2489-2491 claims the learned type drives the SUM, but `addCalc` forces kind `measure`, so the type is never tested there. Only 2792 (kind `null`) tests a default, and that default is kind-based (`app.ts:1535`), not type-based.
- Six checks (1306, 1366, 2500, 2559, and the texts in 4474 and 4566-4588) parse rendered numbers with `replace(/[^0-9.-]/g, '')`. That drops parentheses (the default negative style), commas-vs-decimal locale, `k` scale and units. pnl comparisons are sign-blind as a result. The later window and ad hoc checks read `controller.view` values instead. The earlier ones should too, or compare against database values.
- Sort verification (519-544) uses a text collation (`localeCompare` numeric) as a stand-in for typed ordering. It is correct only for the fixed-width positive id in column 0.
- The harness does its own CONVERTs everywhere it reads values: `Number()` on possibly-bigint or decimal-string values, `String()` as map keys across two query paths, `null -> 0`. These are harness-side mirrors of the runner's Arrow-to-JS conversion. When values arrive with plan-column types (`builder.columns`), the harness can compare typed values exactly.
- `JSON.stringify` over cell values (4633, 4640, 4766, 3114) throws on BigInt. It works today only if the runner never hands Integer over as bigint in the ad hoc view. That is a latent crash tied to the value representation.
- The POV check (4741) compares a stored member value with DOM label text. It only holds for String dimensions. With a typed member (Integer, Date, Boolean) either the check or the product's text-to-literal parse is wrong.
- The pivot cast (`->cast(@Relation<…>)`, 1183/1190, and the comment at 4001) is spelled by the client. The harness checks its position but not its types. The compiler should type the pivot result instead.
- The kind default "fractional -> measure, Integer -> dimension" is pinned by 1994. It diverges from upstream, which sums every numeric (`infer.ts:162-170`), and exists in two client copies (`infer.ts:171` and `snapshot.ts:110/151`, plus serialize.ts 850/1047/1231). The harness depends on it throughout via `.dc-measure`.
- Display defaults keyed on a type string are client presentation decisions: 2 decimals for Float, commas on, parentheses on, integer pivot headers without separators (3335), and Boolean rendered "true". They can stay client side, but the type gate that turns them on should come from the compiler's type.
- Typed filter literals (864-937) are exercised only at "the planner did not refuse" and "5000 appears in the SQL text" level. The date literal kind (StrictDate vs DateTime for trade_date vs booked_at) is not asserted. That belongs to a server literal writer plus a row-count check.
- Exports and clipboard (1596-1604, 1662-1667) assert only non-emptiness. No check covers how Date, Decimal, Boolean or null values are rendered in CSV/HTML/text.
- The sampled data's types are never pinned. A DuckDB sniffer change (DOUBLE to DECIMAL for notional, or booked_at's timestamp form) would silently change the editor, format and kind paths the whole sweep relies on. A first check should assert the source relationType.
