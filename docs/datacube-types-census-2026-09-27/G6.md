## Cross-cutting observations

1. **Group keys are typed values erased to text, then re-guessed.** treeview.ts:105 `groupValue` writes a cell as text: local-component ISO for a Date with milliseconds dropped, and `String(v)` otherwise. tree.ts:20 stores it as `string[]`. serialize.ts `keyValue` re-types it from `ColumnSpec.type` to build filters. plan.ts:133 uses the same rule for pivot tuples. One server fact replaces all four: typed group keys (or opaque key tokens) in the level result, plus a server literal writer for "this key as a filter".
2. **The client invents column types.** treeview.ts:281 (`'Float'` for child aggregates), 426/447 (`'String'` for dimension columns), 441 (`'Any'`, legitimate), and 472 (`'Unknown'`, dead). All except `'Any'` should be the typed plan's column type (compiler: plan columns).
3. **Number format defaults are keyed on the wrong type.** config.ts:539-554 uses the SOURCE column's type, so `avg(Integer)` shows 0 decimals and pivot or child-aggregate columns get no default. The result column's type (and Decimal scale) from the typed plan / `tdsColumns` replaces it.
4. **`isNumericType` / `isFractionalType` are applied in three places here, with three inputs**: config.ts:528 (display defaults), json-shape.ts:313/375 (kind from an inferred kind), and snapshot.ts:108 via `kindOf` (outside G6). A server rule "default role per compiler type" would own them.
5. **json-shape.ts is a complete client type inferencer**: a hand-written JSON parser, a scalar classifier by regex, a widening lattice, a ScalarKind→Pure table (a second type table), and hand-declared types for `size()`, `contains`, `joinStrings` and `sum()`. The replacement is server-side JSON shape inference from the database (typed paths), with each extraction typed by `lambdaRelationType`.
6. **Saved views persist types and lose value types.** persist.ts saves `ColumnSpec.type` (stale until `typeColumns` fixes it, producing `SchemaChange.was`), and turns Date filter/pivot values into UTC ISO strings that are never revived, so they come back as String literals. Values need to be stored as Pure literals written by the server literal writer, and column types need not be stored.
7. **Local-time rendering of dates recurs**: treeview.ts:112-114 and serialize.ts:106-114 (outside G6) both use `getFullYear/getHours` components, while persist.ts:108 uses UTC `toJSON`. That is two conventions for one value. Paths saved in one time zone do not match rows in another.
8. **The NULL group sentinel collides with the path separator** (tree.ts:31 vs serialize.ts:508), which breaks `parsePathKey` for saved expanded null groups. Typed keys with a real null would remove the sentinel.
9. **The step-0 type fetch (cube.ts:426)** is already server-sourced (`lambdaRelationType`). It survives as a separate round trip only because the client keeps its own type state. It would fold into the level plan's typed columns once the client stops storing types.
10. **The snap drops the plan's typed columns** (cube.ts:566), leaving the local database to infer the snap table's types. The plan's columns should drive the snap DDL (server model/DDL).
11. **Pivot draft compile (cube.ts:292-314)** assumes literal types from pivot key NAMES. A server that compiles a pivot draft end to end removes this.
12. **Tree and pivot labels are raw path text** (treeview.ts:396-404, tree.ts:308-313, cube.ts:121-129): no column format, and ISO-local dates. A server-rendered label (or a typed key plus the client's Intl formatter) replaces it.
13. **User choices whose validity depends on type** (config.ts:59-92: format, aggregateFn, wavg weight) are never checked against the type in the client. That is correct under the ruling: the compiler refuses. The UI's list of offered choices by type lives elsewhere (other groups).
